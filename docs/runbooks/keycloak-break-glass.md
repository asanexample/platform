# Runbook: Keycloak Admin-Plane Break-Glass

> **Purpose:** recover administrative control of Keycloak when the normal **passkey-MFA admin login is
> unavailable** — a lost/broken passkey, a misbehaving master-realm browser flow, or platform-realm SSO down.
> The recovery door is the **sealed bootstrap-admin** (`admin-cli` direct-grant), an independent path that does
> **not** depend on any browser flow (ADR-087 INVARIANT; ADR-068 §6 break-glass).
>
> **Severity:** Critical (you are using the keys-to-the-kingdom credential)
> **On-call scope:** Infrastructure / Platform Engineering — **access-admin** authority
> **Decision of record:** [ADR-087](../adrs/087-keycloak-admin-plane-hardening.md)
> **Module paths:** `infra/modules/keycloak/` (the bootstrap-admin secret + seal),
> `infra/modules/keycloak-config/` (the realm flows), the live units under
> `infra/live/aws/platform/us-east-1/platform/keycloak{,-config}/`
>
> **Last reviewed:** 2026-06-28

---

## How the admin plane is hardened (what you are breaking glass *around*)

Keycloak runs two realms, and **both** human console logins are now passkey-gated (ADR-087 + #885):

- **`platform` realm** (the workforce realm) — every workforce login requires a password **and** a
  phishing-resistant passkey (WebAuthn passwordless); no OTP, and self-service "Forgot password" is **off**
  (`enforce_browser_mfa = true`).
- **`master` realm** (the admin console, `/admin/master/console`) — the human console login also requires a
  passkey on top of the password (`manage_master_admin = true` + `enforce_master_browser_mfa = true`, ADR-087).

The one path that is **deliberately left unguarded by any browser flow** is the machine path: the master-realm
`admin` user authenticating with `client_id = admin-cli` via the **direct-grant (password) flow**. This is what
Terraform (`keycloak-config`) uses on every apply, what a from-zero rebuild bootstraps through, **and the
break-glass door**. ADR-087 makes it an **INVARIANT: never disable `admin-cli` direct-grant** — doing so bricks
every rebuild and removes this recovery path.

> **Key consequence:** a broken or locked-out *browser* flow (either realm) never locks out the `admin-cli`
> direct-grant. That is exactly why this runbook works.

## What the sealed bootstrap-admin is, and where its credential lives

| | |
|---|---|
| **Who** | The master-realm `admin` user (username `admin`, the Keycloak 26 "bootstrap admin"). A near-superuser — it manages both realms and itself. |
| **Credential** | A **32-char alphanumeric `random_password`**, generated by the `keycloak` module and stored in **AWS Secrets Manager** at **`platform/keycloak/admin`** (region `us-east-1`, platform account). JSON shape: `{ "username": "...", "password": "..." }`. |
| **In-cluster copy** | External Secrets syncs it to the `keycloak-admin` K8s Secret in the `keycloak` namespace (keys `username`/`password`); Keycloak consumes it as `KC_BOOTSTRAP_ADMIN_USERNAME` / `KC_BOOTSTRAP_ADMIN_PASSWORD`. |
| **Rotation** | The per-rebuild `random_password` regeneration — there is **no separate rotation machinery** (ADR-087). See [Re-seal / rotate](#4-re-seal--rotate-after-use). |
| **Sealed (ADR-087)** | A Secrets-Manager **resource policy** that `Deny`s `secretsmanager:GetSecretValue` to **every** principal whose role is **not** on the sealed-reader allow-list — so **even `AdministratorAccess` cannot read it**. The Deny is scoped to `GetSecretValue` only (`PutResourcePolicy` stays open, so a bad list is always recoverable — never a permanent lockout). |

**The sealed-reader allow-list** (from the live `keycloak` unit's `admin_secret_reader_role_arns`) is exactly
three roles:

1. **PlatformDeployer** (`include.base.locals.deployer_role_arn`) — Terraform reads it on apply.
2. The **External Secrets Operator** role — syncs it into the cluster.
3. **`OrganizationAccountAccessRole`** (in the platform account) — the **break-glass reader**.

Anyone else, including a human signed in with `AdministratorAccess`, gets `AccessDenied` on
`GetSecretValue`. To retrieve the credential you must assume one of those three roles.

## Procedure

### Preconditions

- You can assume a **sealed-reader role** — for break-glass this is
  `arn:aws:iam::<platform-account>:role/OrganizationAccountAccessRole` (the platform account id is in the
  SOPS `secrets.enc.yaml`; `OrganizationAccountAccessRole` is the cross-account break-glass role, see CLAUDE.md
  "IAM Roles"). The deployer role also reads it during normal applies.
- You can reach the **private EKS API** to port-forward to the Keycloak Service. The endpoint is private-only
  (ADR-010): get on **Tailscale** (or the SSM tunnel) per the **`cluster-access`** skill. (During a full
  rebuild the endpoint is briefly public; `platctl` manages that — see
  `docs/runbooks/platform-rebuild-from-scratch.md`.)

### 1. Retrieve the bootstrap-admin credential

Assume a sealed-reader role, then read the secret:

```bash
aws secretsmanager get-secret-value \
  --secret-id platform/keycloak/admin \
  --region us-east-1 \
  --query SecretString --output text
# -> {"username":"admin","password":"<32-char>"}
```

If this returns `AccessDenied`, you are **not** assuming a sealed-reader role (an ordinary `AdministratorAccess`
session is denied **by design**) — re-assume `OrganizationAccountAccessRole` and retry.

Capture the values:

```bash
SECRET=$(aws secretsmanager get-secret-value --secret-id platform/keycloak/admin \
  --region us-east-1 --query SecretString --output text)
KC_USER=$(echo "$SECRET" | jq -r .username)
KC_PASS=$(echo "$SECRET" | jq -r .password)
```

### 2. Reach the admin API over the `admin-cli` direct-grant

The break-glass door is **programmatic** (`admin-cli` direct-grant), not the console — the console still wants a
passkey, but the direct-grant flow does not. Reach Keycloak the same in-cluster way `keycloak-config` does: a
port-forward to the Keycloak Service (the repo helper assumes the deployer role to reach the cluster).

```bash
# scripts/kc-portforward.sh up <cluster> <region> <role_arn> <namespace> <service> <remote_port> <local_port>
# Mirrors the keycloak-config before_hook: forwards the keycloak Service to localhost:18080.
scripts/kc-portforward.sh up \
  <eks-cluster-id> us-east-1 <PlatformDeployer-arn> keycloak keycloak 80 18080
```

(Or, with a working kubeconfig: `kubectl -n keycloak port-forward svc/keycloak 18080:80`.)

Now obtain an admin token via the master-realm direct-grant (this is the path that bypasses the browser passkey
flow):

```bash
curl -s http://localhost:18080/realms/master/protocol/openid-connect/token \
  -d client_id=admin-cli -d grant_type=password \
  -d "username=${KC_USER}" -d "password=${KC_PASS}" | jq -r .access_token
```

A token here proves the recovery door works. Use it against the Admin REST API, or — equivalently — drive
`kcadm.sh` (it ships inside the Keycloak container) via `kubectl exec` into the keycloak pod and
`kcadm.sh config credentials --server http://localhost:8080 --realm master --user "$KC_USER"`.

When done, tear the forward down: `scripts/kc-portforward.sh down <eks-cluster-id> 18080`.

### 3. Do the recovery

Common break-glass actions, depending on *why* you are here:

- **A user lost their passkey / is locked out of the platform realm.** Reset their credentials and force
  re-enrollment: remove the user's WebAuthn credential and add the `webauthn-register-passwordless` required
  action (the same one the flow force-enrolls), so they enroll a fresh passkey on next login. Recovery is "a
  backup passkey or admin re-provision" by design (no self-service reset).
- **The master-realm browser flow itself misbehaves (you can't get into the console at all).** The documented
  fix is to **revert the binding**: set `enforce_master_browser_mfa = false` in the `keycloak-config` unit and
  re-apply (`admin-cli` direct-grant is independent of any browser flow, so this is safe). The platform-realm
  analogue is `enforce_browser_mfa = false`. After fixing the flow, re-bind with the two-apply, no-lockout
  discipline (build → enroll a passkey on `admin` → bind).
- **App SSO is down but you need ArgoCD/Backstage.** That is a *different* break-glass — ArgoCD has its own
  local-admin fallback; see [secret-rotation.md §4](secret-rotation.md#4-argocd-oidc-client-secret-rotation)
  and [identity-sso-troubleshooting.md](identity-sso-troubleshooting.md).

> If a specific recovery step (e.g. the exact `kcadm.sh` invocation for your action) is not spelled out here,
> **confirm with the platform owner** before running it against the live master realm — this is the
> highest-blast-radius credential in the system.

### 4. Re-seal / rotate after use

Using the credential does **not** un-seal the secret — the resource policy is unchanged by a `GetSecretValue`,
so there is nothing to "re-seal" after a read. Two follow-ups apply:

- **Audit the access.** Every `GetSecretValue` on `platform/keycloak/admin` is recorded in CloudTrail
  (ADR-037). Confirm the only reads in the window were yours:

  ```bash
  aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=ResourceName,AttributeValue=platform/keycloak/admin \
    --start-time "$(date -u -v-7d '+%Y-%m-%dT%H:%M:%SZ')" \
    --region us-east-1 \
    --query 'Events[].{Time:EventTime,Name:EventName,User:Username}' --output table
  ```

- **Rotate the credential** if it may have been observed. ADR-087's rotation model is the per-rebuild
  `random_password` regeneration. To rotate **without** a full rebuild, force a new value by replacing the
  generated password and re-applying the `keycloak` unit, which writes the new `platform/keycloak/admin` value
  and lets External Secrets re-sync the in-cluster `keycloak-admin` Secret:

  ```bash
  cd infra/live/aws/platform/us-east-1/platform/keycloak
  # AWS_PROFILE=management (apply assumes PlatformDeployer). Verify the plan shows ONLY the admin
  # password + secret-version replacing — nothing else — before approving.
  terragrunt apply -replace='random_password.admin[0]'
  ```

  **Confirm with the owner before running this on the live cluster** — a botched replace of the bootstrap
  admin is exactly the failure mode the INVARIANT guards against. The exact resource address / whether an
  out-of-band rotation is preferred over waiting for the next rebuild is an owner call; this runbook does not
  assert it has been exercised live.

  After rotation, verify the new credential authenticates (repeat [step 2](#2-reach-the-admin-api-over-the-admin-cli-direct-grant)
  with the freshly-read secret) and that the in-cluster `keycloak-admin` Secret has re-synced
  (`kubectl -n keycloak get secret keycloak-admin`).

## Do-not / invariants

- **Never delete the `admin` user.** Keycloak 26 nags you to "create a permanent admin and delete the
  temporary one" — ADR-087 records that we **keep it on purpose**. Terraform authenticates as it, the rebuild
  recreates it, and it is this break-glass door. Deleting it bricks the platform.
- **Never disable `admin-cli` direct-grant** (the ADR-087 INVARIANT). The master browser-flow hardening is
  *additive* to this door, never a replacement.
- **Don't add yourself to the sealed-reader list to make a read convenient.** Assume
  `OrganizationAccountAccessRole`. Widening the allow-list weakens the seal for everyone.
